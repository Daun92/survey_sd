# AI 인터뷰형 CS 설문 기획안 (하이브리드)

Oct 19, 2026 · @정다운

## 0. 취지와 배경

이 절은 처음 보는 세션이 "왜 이 일을 하는지, 무엇이 이미 있는지, 어떤 전제로 설계했는지"를 한 번에 알도록 쓴 것이다. 처음이면 0 → 1 → 2 → 12 → 14 순으로 읽은 뒤 나머지를 본다.

**회사와 역할**

- 엑스퍼트컨설팅: B2B HRD/L&D 컨설팅·교육 기업. 고객사 HRD 담당자에게 리더십·직무·조직개발 교육을 제안하고 수행
- 다운(영업기획): 이 저장소(exc-survey)를 혼자 설계·개발·운영. 전담 개발 인력이 없어 Claude Code가 개발 파트너이고, 이 문서가 세션 간 공통 기억
- 등장인물: AM(수주·고객 관계), IM(현장 운영·사후 관리), 수행팀(과정 설계·강사 섭외·콘텐츠 개발), 강사, 고객사 HRD 담당자(응답자), 팀장(결과 활용)

**CS 설문의 현재 위치**

- 대상: 교육 프로젝트 종료 후 고객사 담당자에게 보내는 사후 만족도 조사(S1). 프로젝트당 1회, 실명
- 구성: 5점 리커트 정량 — 교육 만족(전반·목적부합·재구매의향·추천의향), 담당자(8문항), 강사(8문항), 에코시스템(1문항) — 와 주관식(소감, 장단점, 개선·추가 요청)
- 쓰임: 재구매의향·추천의향은 AM·팀 KPI와 고객유지·교차판매 예측에 연결, 담당자·강사 점수는 서비스 품질 관리
- 채널: 온라인 폼(이메일·SMS 토큰 링크)과 전화 인터뷰 대리 입력의 이중 채널, 월간 배치 자동 발송
- 방향: CS 운영이 "만족도 측정과 보고서"에서 "다음 거래 예측과 AM 행동"으로 전환 중(`HARNESS.md`) — 재계약 시그널 문항, BRIS place\_id 연결, AM 주간 액션 리스트

**왜 지금 인터뷰인가**

- 계기(확인됨): 다운이 Anthropic Economic Index Survey에 응답하며 Anthropic Interviewer를 경험. AI가 답변에 따라 후속 질문을 바꿔 가며 캐묻는 방식을 우리 사후 CS 설문에 적용하고자 함
- 문제 가설 1: 주관식 문항은 한두 줄 답이 대부분이고 "왜"가 빠짐 — 점수는 있는데 행동으로 옮길 근거가 없음
- 문제 가설 2: 전화 인터뷰는 깊이는 있으나 AM·CS 시간이 들고 기록이 담당자 메모에 흩어짐
- 문제 가설 3: 정성 응답이 리포트 VOC 탭에 쌓여도 구조화되지 않아 AM이 읽지 않음
- 가설 3개는 다운의 해석을 정리한 것으로, 실고객 파일럿(11절)에서 참여율·AM 평가로 확인

**기대 효과**

- 정성 응답의 양과 깊이 증가 — 주제별 구체 사례와 요청 사항
- 종료 즉시 구조화 → AM이 30초에 읽는 요약, 위험 신호 당일 전달
- 전화 인터뷰를 플래그 건·미참여자로 축소
- 가이드와 추출 결과가 쌓여 다음 설문 설계의 근거가 됨 — 반복 가능한 자산

**설계 원칙 (왜 하이브리드인가)**

- 정량은 폼에 둔다: KPI에 연결된 척도의 일관성과 과거 데이터와의 비교 가능성
- 정성만 대화로: 가치가 생기는 곳은 "왜 그렇게 평가했는가"
- LLM은 점수를 매기지 않는다: Anthropic 사례에 "인터뷰어가 자기 인터뷰를 채점한다"는 비판이 있었고, 우리 데이터는 KPI로 쓰임
- 기존 폼·발송·집계 코드는 보존: `AGENTS.md` 원칙, 되돌리기 쉬운 추가 방식
- 가이드는 코드가 아니라 데이터: 질문·탐침 수정에 배포가 필요 없어야 함
- 사람 검수를 전제로: 추출 결과는 검수 후 집계

**결정 이력**

- 2026-10-19: 구상 → A안(하이브리드) 확정. B안(전체 대화형)은 KPI 척도 단절·응답률 위험·구현 범위를 이유로 폐기
- 참고 구조(Anthropic Interviewer): 계획(연구자가 목표 정의 → 모델이 가이드 초안 → 사람이 확정) → 인터뷰(실시간, 적응형 후속 질문, 참여자 언어) → 분석(결과를 연구자에게). 참여 전 활용 고지, 마지막 열린 질문. 이 문서의 5·6절(계획), 4절(인터뷰), 7·8절(분석)이 각각 대응

**용어**

| 용어 | 뜻 |
| --- | --- |
| AM | Account Manager — 수주·고객 관계 담당 |
| IM | Instructor Manager — 현장 운영·사후 관리 담당 |
| 수행팀 | 과정 설계·강사 섭외·콘텐츠 개발 (리더십, 업무성과, 변화디자인 등 솔루션별) |
| S1 | CS 만족도 조사 — 플랫폼 설계상 설문 유형 번호 |
| 에코시스템 | 정량 문항에 나오는 자사 온라인 학습 지원 시스템 — 인터뷰 설계에서는 명칭만 그대로 사용 |
| BRIS / place\_id | 사내 영업 시스템과 사업장 코드 — 수주·방문·건강도 데이터의 연결 키 |
| dash\_erp | BRIS 기반 영업 대시보드 — 인터뷰 추출 결과의 최종 소비처 |
| cs-bridge | 외부 CS 대상자 관리 시스템 ↔ exc-survey 연동 API |
| 추출 | 대화 원문에서 요약·항목·플래그를 구조화해 뽑는 LLM 처리 (7절) |
| 검수 | 추출 결과를 사람이 확인·수정해 `reviewed`로 바꾸는 일 (8절) |

**이 문서의 위치**

- Claude Code 세션의 단일 기준 문서. 확정 결정은 `docs/interview/decisions.md`, 진행 기록은 `docs/interview/worklog/`에 쌓는다
- 관련 문서: `HARNESS.md`(영업기획 CS 전환 방향), `docs/PRD.md`, `docs/cs-integration/*`(연동 설계와 결정 기록 형식)

## 1. 목적과 범위

정량 폼은 그대로 두고, 정성·주관식 구간만 AI 인터뷰어와의 대화로 바꾼다. A안(하이브리드)으로 2026-10-19 확정.

**목적**

- 전화 인터뷰와 주관식 문항으로 받던 "왜 그렇게 평가했는가"를 AI 인터뷰어가 후속 질문으로 캐묻는 대화로 수집
- 자유 응답을 종료 즉시 구조화해 AM·팀장이 바로 쓰는 데이터로 전환
- Anthropic Interviewer의 3단계(계획 → 인터뷰 → 분석)를 CS 설문 규모에 맞게 축소 적용

**범위**

- 대화로 대체: 정성 주관식(전반 소감, 강사·강의 아쉬운 점, 담당자·현장운영 피드백, 기타 개선의견, 차년도 과업·키워드)과 기존 "인터뷰 참여" 섹션
- 유지: 정량 리커트 전 문항(교육 만족·담당자·강사·에코시스템), 발송·토큰·관리자 화면, KPI 집계
- 신규: 인터뷰 화면, 대화 처리, 저장, 종료 시 구조화 추출, 관리자 열람

**비범위**

- 정량 점수의 대화 수집이나 LLM 추정 (KPI 척도 일관성 유지)
- 음성 인터뷰, 실시간 상담, 자동 답변 메일
- 교육생 대상 설문(S2·S3)에 적용 — CS 설문(S1) 안정화 후 별도 검토

**성공 기준 (파일럿에서 확인, 제안값 — 파일럿 전 확정)**

| 기준 | 제안값 | 측정 방법 |
| --- | --- | --- |
| 완료율 | 기존 폼 완료율 대비 -10%p 이내 | 인터뷰 시작 대비 종료 건수 (현재 폼 완료율 수치 확인 필요) |
| 정보량 | 응답당 채워진 추출 항목 수가 기존 주관식 평균보다 많음 | 추출 결과 테이블 집계 |
| 추출 정확도 | 검수 시 수정률 20% 이하 | 검수 화면에서 수정 건수 기록 |
| 응답 시간 | 중앙값 10분 이내 | 세션 시작·종료 시각 |

## 2. 현재 시스템과 변경 범위

인터뷰는 exc-survey(저장소 `Daun92/survey_sd`) 안에 응답자 경로 1개와 테이블 4개를 더하는 작업이며, 기존 폼·제출·집계 코드는 건드리지 않는다. 아래 현황은 2026-10-19 `main` 코드를 직접 확인한 내용.

**현재 구조 (확인 완료)**

| 영역 | 현재 상태 | 인터뷰 설계에 미치는 점 |
| --- | --- | --- |
| 스택 | Next.js 16.2.1 App Router, React 19, Supabase 단일 소스(Prisma는 2026-04 제거), Vercel 자동 배포 | 신규 코드도 server action·API route·Supabase 패턴 유지 |
| CS 설문 생성 | `cs_survey_templates`·`cs_survey_questions`(부문별 기본 템플릿) → quick-create → `edu_surveys`(survey\_type `cs_satisfaction`) + `edu_questions` | 인터뷰 ON/OFF는 `edu_surveys.settings` 플래그로 설문 단위 제어 |
| 응답 경로 | `/s/[token]` 공통 링크, `/d/[token]` 개인 링크(`distributions.unique_token`) → `SurveyForm`(landing → 섹션별 문항 → ending) | 두 경로 모두 같은 ending 화면을 쓰므로 진입 버튼 1곳만 추가 |
| 제출 | `POST /api/surveys/[token]/submit` → `edu_submissions.answers` JSONB(문항 id → 값), `distributions.status = completed` | 제출 응답에 인터뷰 토큰을 실어 보내면 세션 연결이 끝남 |
| 문항 유형 | likert\_5/6, single\_choice, multiple\_choice, text, yes\_no, info\_block, `skip_logic.show_when` | 정량 문항·에코 분기는 그대로 둠 |
| 설문 설정 | `settings` JSONB: welcome\_message, privacy\_consent\_text, require\_consent, ending\_title, thank\_you\_message 등 | 인터뷰 설정도 같은 JSONB에 추가 |
| 발송 | `/admin/distribute`, `distribution_batches`·`distributions`, 이메일(HIWORKS·SMTP)·SMS(PPURIO) 큐 + cron | 변경 없음. 인터뷰 링크는 폼 제출 뒤 발급 |
| CS 연동 | `cs_survey_targets`·`cs_target_batches`·`cs_contacts`, BRIS place\_id, 월간 배치 cron, cs-bridge API | 인터뷰 결과도 `distributions`를 통해 place\_id까지 연결 가능 |
| AI | `src/lib/gemini.ts`(fetch 직접 호출, JSON 응답 강제), `app_settings.gemini_api_key`, `/api/ai/*` 3종 | 같은 호출 패턴으로 인터뷰용 모듈 작성 |
| 리포트 | `/admin/reports` 5탭(요약·개별·세그먼트·VOC·히트맵), `/admin/responses/[surveyId]` | VOC 탭과 응답 상세에 인터뷰 결과를 붙임 |

**바뀌는 것**

- 응답자: 폼 ending 화면에 "인터뷰 이어하기" 카드 추가, 새 경로 `/i/[token]`에서 대화 진행
- 데이터: 인터뷰 가이드·세션·메시지·추출결과 테이블 신설, 세션은 `edu_submissions` 1건에 1:1 연결
- 처리: 대화 턴 API, 종료·추출 API, 추출 실패 재시도 cron
- 관리자: 응답 상세에 인터뷰 탭(요약·추출 항목·원문·검수), 설문 설정에 인터뷰 ON/OFF와 가이드 선택, VOC 탭 집계
- 설정: 인터뷰용 모델 키 (제공자·보관 위치는 9절에서 결정)

**유지하는 것**

- `edu_questions` 문항, 점수 산출, 리포트 집계, KPI 연동 전부
- `/s`·`/d` 폼 동작 — AGENTS.md "응답자 라우트 기존 동작 보존" 원칙에 따라 변경은 ending 화면 카드 1개와 settings 플래그로 한정
- 발송 채널, 토큰 체계, `distributions` 상태 흐름
- 기존 text 문항: 파일럿 동안 유지(인터뷰 미참여자 폴백) → 운영 전환 시 템플릿에서 제거 여부 결정

## 4. 응답자 경험

폼 제출 직후 같은 화면에서 "5분만 더 말씀해 주시겠어요?"로 시작하고, 지금 못 하면 같은 링크로 나중에 이어갈 수 있게 한다.

**진입**

- 위치: 폼 ending 화면의 감사 문구 아래 카드 — "AI 인터뷰어와 5\~10분 대화 (선택)" + 버튼 "지금 시작" / "나중에 하기"
- 조건: 설문 `settings.interview_enabled = true`이고 제출이 성공해 submission id가 있을 때만 표시
- 링크: `/i/[interview_token]` — 제출 API가 발급해 응답에 실어 보냄. `distributions.unique_token`과 별개이므로 공통 링크(`/s`) 응답도 인터뷰 가능
- "나중에 하기": 1차는 링크 복사 안내까지. 이메일 재발송은 파일럿 결과를 본 뒤 결정

**화면 흐름 (`/i/[token]`)**

1. 시작 화면 — 목적, 예상 시간, 고지(음성 녹음 없음, 대화 원문이 저장되어 엑스퍼트컨설팅 담당 팀이 열람, 보존 기간), 동의 체크 → "시작"
2. 대화 화면 — 기존 `MobileFrame`(420px) 유지. 인터뷰어 말풍선, 입력창, 상단에 "주제 3/6" 진행 표시. 전송 중 입력 잠금과 타이핑 표시
3. 보조 조작 — "이 주제 건너뛰기"(다음 주제로), "여기서 마치기"(현재까지 저장 후 종료 절차)
4. 종료 화면 — 감사 문구 + "의견은 담당 팀에 전달됩니다". 응답자에게 요약을 보여주는 기능은 2차 검토(응답자 확인 부담 대비 효과 미확인)

**이어하기**

- 메시지마다 서버 저장. 같은 링크로 재진입하면 마지막 인터뷰어 질문부터 재개
- 세션 상태: `not_started → in_progress → completed | abandoned`
- `abandoned`: 마지막 메시지 후 48시간 무응답이면 cron이 전환하고, 수집된 범위에서 추출은 수행

**종료 조건**

- 가이드의 핵심 주제를 모두 다뤘을 때, 15턴 상한, 또는 응답자의 종료 요청
- 종료 직전에 반드시 열린 질문 1개("설문에 없었지만 전하고 싶은 말씀")

**지연·장애 처리**

- 모델 응답 10초 초과: "잠시만 기다려 주세요" 표시
- 30초 초과 또는 오류 2회: "답변을 받지 못했습니다. 아래 칸에 적어 주시면 그대로 저장됩니다" — 남은 주제를 text 입력 1개로 받는 폴백
- 폴백 응답도 같은 세션에 `system` 메시지로 저장해 추출 대상에 포함

## 5. 인터뷰 가이드 v1

핵심 주제 6개를 "열린 질문 1개 + 탐침 규칙"으로 구성하고, 전체를 10분·15턴 안에 끝낸다. 문구는 데스크 테스트(10절) 뒤 v2로 다듬는다. 가이드는 코드가 아니라 DB 데이터(`interview_guides`)로 두어 코드 배포 없이 바꾼다.

**목표**

- 정량 점수 뒤의 이유와 구체 사례 수집
- 담당자(AM)·강사·운영 각각의 개선 요청을 행동 가능한 수준까지 구체화
- 차년도 교육 과업·관심 주제(재계약 시그널의 정성 근거) 파악

**사전 맥락 (인터뷰어에게 주입, 응답자에게 노출 금지)**

- 고객사명, 과정명, 교육유형, 담당 AM명, 강사명
- 정량 응답 요약: 낮은 점수 상위 2개 영역, 높은 점수 상위 2개 영역 — 점수를 말하지 않고 탐침 순서를 정하는 데만 사용

**핵심 주제와 질문**

| 순서 | 주제 | 열린 질문 (초안) | 탐침 규칙 | 추출 항목 |
| --- | --- | --- | --- | --- |
| 1 | 전반 소감 | 이번 과정을 한 문장으로 평가하신다면 어떻게 말씀하시겠어요? | "가장 기억에 남는 장면"으로 구체화 1회 | overall\_sentiment, highlight |
| 2 | 만족한 점 | 특히 좋았던 점은 무엇이었나요? | 담당자·강사·내용·운영 중 어디 이야기인지 드러날 때까지 1회 | strengths\[\] |
| 3 | 아쉬운 점 | 아쉽거나 기대와 달랐던 점이 있었다면요? | 낮은 점수 영역이 있으면 그 영역부터. "어떻게 달라졌으면 하는지" 1회 | improvements\[\] |
| 4 | 담당자·운영 | 담당자와의 소통이나 준비·운영 과정은 어떠셨어요? | 응답 속도·사전 파악·사후 관리 중 응답자가 꺼낸 것만 심화 | am\_feedback |
| 5 | 강사·강의 | 강의와 강사에 대해 더 하실 말씀이 있을까요? | 맞춤화·사례·전달력 중 응답자가 꺼낸 것만 심화 | instructor\_feedback |
| 6 | 다음 계획 | 내년이나 다음 분기에 고민 중인 교육 주제나 과제가 있으세요? | 시기·대상·주제 중 빠진 것 1회 | next\_needs\[\], timing\_hint |
| 끝 | 열린 질문 | 설문에 없었지만 전하고 싶은 말씀이 있다면요? | 없음 | other\_comments |

**순서 규칙**

- 주제 1은 항상 첫 질문. 낮은 점수 영역이 있으면 주제 3을 그 영역으로 특정해 두 번째로 당김
- 응답자가 먼저 꺼낸 주제는 재질문하지 않고 "앞서 말씀하신 … 외에"로 이어감
- 주제 4·5는 정량 응답에서 담당자·강사 점수가 모두 높고 응답자가 언급하지 않으면 질문 1개로 합침

**탐침 공통 규칙**

- 추상적 답변("좋았다", "아쉬웠다")에는 구체 사례 1회 요청, 그래도 추상적이면 넘어감
- 한 주제당 후속 질문 최대 2회
- 답변 길이에 비례해 묻는다 — 짧게 답하면 짧게

**금지 영역**

- 특정 인물(AM·강사)에 대한 점수·등급 요구
- 타사 비교, 가격·계약 조건, 사내 인사 정보 — 묻지 않고, 응답자가 말해도 더 캐묻지 않음
- 회사 입장 변호, 사과, 약속("개선하겠습니다") — "담당 팀에 전달하겠습니다"까지만

**종료 조건**

- 6주제 완료, 15턴 도달, 10분 경과 안내 후 응답자 선택, 응답자 종료 요청 중 하나
- 어떤 경우든 마지막 열린 질문 1개 뒤에 종료 인사

## 6. 인터뷰어 행동 규칙 (프롬프트 사양)

프롬프트는 "역할·맥락·가이드·규칙·출력" 5블록으로 고정하고, 가이드 블록만 DB에서 바꿔 끼운다. 주제 순서와 턴 상한은 모델이 아니라 서버가 통제한다.

**프롬프트 블록**

| 블록 | 내용 | 출처 |
| --- | --- | --- |
| 역할 | 엑스퍼트컨설팅 CS 팀의 인터뷰어. 존댓말, 짧은 문장, 한 번에 질문 하나 | 코드 상수 |
| 맥락 | 고객사·과정·교육유형·AM·강사·정량 요약(5절) | 세션 생성 시 주입 |
| 가이드 | 5절의 주제·질문·탐침·금지 | `interview_guides` (버전 관리) |
| 규칙 | 아래 행동 규칙 | 코드 상수 |
| 출력 | 매 턴 JSON 1개: `{say, topic_id, topic_done, interview_done, flags[]}` | 코드 상수 |

**행동 규칙**

- 질문은 한 번에 하나. 두 개를 묻고 싶으면 다음 턴으로 미룸
- 평가·공감 과잉 금지: "말씀 감사합니다" 수준까지. "정말 훌륭한 지적입니다" 류 금지
- 유도 금지: 선택지를 제시하지 않음 ("A 때문인가요, B 때문인가요?" 금지)
- 응답자 말을 바꿔 말할 때 의미를 더하지 않음
- "모르겠다"·답변 거부 → 즉시 다음 주제
- 개인정보·타사·계약 조건이 나오면 후속 질문 없이 `flags`에만 기록
- 12턴 또는 10분 도달 시 "두 가지만 더 여쭙겠습니다" 안내
- 마지막은 열린 질문 1개 → 종료 인사. 종료 인사에 약속·사과 없음

**출력 JSON 필드**

| 필드 | 용도 |
| --- | --- |
| `say` | 응답자에게 보일 발화 (1\~3문장) |
| `topic_id` | 지금 다루는 주제 — 화면의 "주제 3/6" 표시 |
| `topic_done` | 모델이 주제 종료를 제안 — 서버가 수용 여부 결정 |
| `interview_done` | 종료 제안 — 서버가 열린 질문 여부·턴 수를 확인한 뒤 수용 |
| `flags[]` | `competitor_mention`, `contract_terms`, `personal_info`, `distress` — 추출 단계와 검수 우선순위에 전달 |

**턴 제어 (서버 책임)**

- 매 호출에 "현재 주제, 남은 주제, 현재 턴/상한, 이번 주제의 후속 질문 횟수"를 명시해 보냄
- `topic_done = true`이거나 주제별 후속 2회 초과 시 다음 주제로 강제 전환
- 15턴 도달 시 `interview_done`과 무관하게 마무리 질문 단계로 진입
- JSON 파싱 실패 2회 → 같은 턴 재시도 1회 → 실패 시 4절의 text 폴백
- 모델 호출은 서버에서만. 키·프롬프트는 응답자 브라우저에 내려가지 않음

## 7. 데이터 설계 (업무 관점)

저장은 "세션 1건 + 메시지 N건 + 추출 결과 1건"이고 셋 다 기존 응답(`edu_submissions`) 1건에 매달린다. 컬럼명·타입은 Claude Code 세션에서 기존 마이그레이션 관례에 맞춰 정한다.

**무엇을 저장하는가**

| 대상 (제안 테이블) | 저장 항목 | 왜 필요한가 |
| --- | --- | --- |
| 인터뷰 가이드 (`interview_guides`) | 이름, 버전, 대상 설문 유형, 주제·질문·탐침·금지 JSON, 활성 여부 | 코드 배포 없이 가이드 교체, 버전별 결과 비교 |
| 세션 (`interview_sessions`) | 어느 응답·설문·배포·응답자에 속하는지, 가이드 버전, 상태, 접근 토큰, 동의 시각, 시작·종료 시각, 턴 수, 종료 사유, 테스트 여부 | 완료율·소요시간 측정, 이어하기, 테스트 제외 |
| 메시지 (`interview_messages`) | 순서, 화자(인터뷰어·응답자·시스템), 본문, 주제 id, 시각, 모델명, 토큰 수, 지연(ms), flags | 원문 열람, 비용·품질 추적 |
| 추출 결과 (`interview_extractions`) | 아래 추출 스키마 전체, 추출 모델·프롬프트 버전, 검수 상태(unreviewed/reviewed), 검수자, 수정 전 원본 | 대시보드·알림, 검수, 정확도 측정 |

**추출 스키마 v1** — 종료 직후 1회, 대화 원문 전체가 입력

| 항목 | 형태 | 비고 |
| --- | --- | --- |
| `summary` | 2\~3문장 | AM이 30초에 읽는 요약 |
| `overall_sentiment` | positive / neutral / negative / mixed | 정량 점수와 교차 확인용. 점수가 아님 |
| `strengths[]` | `{area, text, quote}` — area: am / instructor / content / operation / system | 항목마다 원문 인용 1개 |
| `improvements[]` | `{area, text, request, severity, quote}` — severity: low / mid / high | severity는 응답자 표현 강도 기준 |
| `am_feedback` | 문장 | 담당자 관련 발언 요약 |
| `instructor_feedback` | 문장 | 강사 관련 발언 요약 |
| `next_needs[]` | `{topic, target, timing, text}` | 영업 시그널 — 재계약 시그널 문항의 정성 근거 |
| `risk_flags[]` | churn\_signal / complaint\_unresolved / escalation\_request / competitor\_mention | 알림 트리거 |
| `keywords[]` | 최대 8개 | VOC 탭·검색 |
| `confidence` | 0\~1 | 낮으면 검수 우선 |

**기존 정성 코드와의 대응** — 2025-12 DB 설계의 QF\_01\~07

| 기존 코드 | 추출 항목 |
| --- | --- |
| QF\_01 전반적 만족도 | `summary`, `overall_sentiment` |
| QF\_02 강사·강의 만족 | `strengths[]` area=instructor, `instructor_feedback` |
| QF\_03 강사·강의 아쉬운 점 | `improvements[]` area=instructor |
| QF\_04 담당자 만족도 | `am_feedback`, area=am 항목 |
| QF\_05 현장운영 만족도 | area=operation 항목 |
| QF\_06 기타 개선의견 | `improvements[]` 나머지 |
| QF\_07 차년도 과업·키워드 | `next_needs[]`, `keywords[]` |

**연결 규칙**

- 세션은 submission 1건당 최대 1건. 같은 링크 재진입은 기존 세션 재개
- 응답자 식별은 submission의 `respondent_id`·`distribution_id`를 따라감. 공통 링크 응답은 익명 유지
- 테스트 제출(`is_test`)의 세션은 집계·알림·검수 큐에서 제외
- 접근 권한: 응답자(anon)는 자기 토큰의 세션·메시지만 읽고 쓰기, 추출 결과는 서버(service role)와 관리자만
- 보존: 원문은 제안 2년 뒤 삭제, 추출 결과는 유지 — 기간은 확인 필요(사내 개인정보 정책)

## 8. 분석·활용 흐름

종료 즉시 자동 추출하고, 위험 플래그가 있는 건은 당일 담당자에게 보이며, 나머지는 검수를 거쳐 리포트에 반영한다.

1. 종료(또는 abandoned 판정) → 추출 실행 → `interview_extractions` 저장, 검수 상태 `unreviewed`
2. `risk_flags`가 있으면 담당 AM·팀장에게 알림 — 1차는 `/admin` 사이드바 배지와 응답 목록 강조. 기존 `cs_dispatch_alerts` 체계로 보낼 수 있는지는 확인 필요
3. 검수 — `/admin/responses/[surveyId]` 목록에 "인터뷰" 열(상태·플래그) 추가, 상세에서 요약·추출 항목·원문을 보고 수정 → `reviewed`. 수정 전 원본은 보관해 정확도 측정에 사용
4. 리포트 — `/admin/reports` VOC 탭에 인터뷰 집계 블록 추가: area별 `improvements` 빈도, `keywords` 상위, `risk_flags` 건수. 기존 서술형 Gemini 분석과 나란히 표시
5. 대시보드(dash\_erp) — 추출 결과 뷰 `v_interview_extractions`(세션 메타 + 추출 항목 + place\_id)를 제공하고 외부 대시보드가 읽음. place\_id는 `distributions → cs_survey_targets` 경유

**검수 운영 기준**

- 파일럿: 전수 검수
- 운영 전환 후: 샘플 20% + `risk_flags` 전수 + `confidence < 0.6` 전수
- 수정률(수정 건수 ÷ 검수 건수)을 월별로 기록 — 1절 성공 기준의 측정값

**AM이 보는 화면 (최소 구성)**

- 응답 상세 상단: `summary` 2\~3문장, `overall_sentiment`, 플래그
- 중단: `strengths`·`improvements`를 area별로 묶어 표시, 각 항목에 원문 인용
- 하단: `next_needs` — 영업 후속 행동의 근거
- 원문 전체는 접힘 상태로

## 9. 기술 결정 사항 (Claude Code 세션에서 확정)

결정 6개는 코드 확인을 마친 뒤 Claude Code 세션 첫 단계에서 확정한다. 각 항목에 기본안을 두었고, 코드베이스 사실과 어긋나면 기본안을 바꾼다.

| 번호 | 결정 | 선택지 | 영향 | 기본안 |
| --- | --- | --- | --- | --- |
| D1 | 모델 제공자 | (a) Claude API 신규 연결 (b) 기존 Gemini 재사용 | (a) 대화 품질·구조화 출력에 유리, 키·비용 라인 추가 (b) 코드·설정 UI 재사용, 모델 교체 쉬움 | (a). 단 `gemini.ts`처럼 fetch 직접 호출·JSON 강제 패턴을 따라 `src/lib/interview-llm.ts`를 제공자 교체 가능하게 작성 |
| D2 | 응답 전달 방식 | (a) 스트리밍 (b) 턴 단위 완성 응답 | (a) 체감 속도, JSON 출력과 충돌·구현 복잡 (b) 단순, 2\~5초 대기 | (b) + 타이핑 표시. 1턴이 1\~3문장이라 대기가 짧음 |
| D3 | 상태 저장 위치 | (a) 메시지마다 DB (b) 클라이언트 보관 후 종료 시 일괄 | (a) 이어하기·이탈 분석 가능, 쓰기 많음 (b) 쓰기 적음, 이탈 시 유실 | (a) |
| D4 | 추출 실행 시점 | (a) 종료 요청 처리 안에서 동기 (b) 큐 + cron | (a) 단순, 종료 화면 5\~10초 지연 (b) 기존 cron 패턴 재사용, 지연 없음 | (a) 종료 화면을 먼저 보여주고 백그라운드 호출, 실패분만 cron 재시도 |
| D5 | 인터뷰 진입 경로 | (a) `/i/[token]` 별도 라우트 (b) `/s`·`/d` 폼 안에 단계 추가 | (a) 폼 코드 불변, 링크 재진입 가능 (b) 화면 일관, 폼 코드 변경 | (a) — AGENTS.md 보존 원칙 |
| D6 | API 키 보관 | (a) `app_settings` 행 (b) Vercel 환경변수 | (a) 관리자 UI에서 교체, DB 노출 범위 넓음 (b) 배포 없이 교체, UI 없음 | (b) 기본 + `app_settings` 값이 있으면 우선 |

**기술 메모 (코드 확인 완료)**

- 새 API: `POST /api/interviews/[token]/message`, `POST /api/interviews/[token]/finish` — `withAuth({ type: 'public' })` 패턴, 토큰으로 세션 식별
- 세션 생성: `/api/surveys/[token]/submit` 응답에 `interview_token` 추가 — `settings.interview_enabled`일 때만 생성, 응답 저장 트랜잭션과 분리해 실패가 제출에 영향 없게
- 마이그레이션: 14자리 타임스탬프 파일명, idempotent 체크리스트, RLS — anon은 자기 토큰 세션·메시지만, 추출 결과는 service role·authenticated만
- 모델명·가격: 구현 시점에 docs.claude.com에서 확인해 `decisions.md`에 기록 (이 문서에는 적지 않음)
- 비용 상한: 세션당 턴 15, 추출 1회, 월 세션 한도 `app_settings.interview_monthly_cap` — 초과 시 ending 카드 숨김
- 스트리밍을 나중에 켤 경우 `say`만 스트리밍하고 메타는 끝에 붙이는 구조로 바꿀 수 있게 응답 형식을 분리

## 10. 테스트 계획

가이드 품질은 코드 전에 데스크 테스트와 모의 응답자 6종으로, 코드는 단위·E2E로 검증한다. 추출 정확도는 수기 코딩과 비교해 수치로 남긴다.

**데스크 테스트 (코드 작성 전)**

- Claude.ai에서 6절 프롬프트 + 5절 가이드로 모의 인터뷰 10회 (다운이 고객 역할)
- 체크 항목: 질문 하나씩 / 선택지 제시 없음 / 주제 전환 자연스러움 / 10분 내 종료 / 마지막 열린 질문
- 결과: 통과 7회 이상이면 가이드 v1 확정, 미달이면 문구 수정 후 재시도. 로그는 `docs/interview/desk-test/`에 저장

**모의 응답자 시나리오 (구현 후, 단위·수동 공통)**

| 시나리오 | 응답자 행동 | 통과 조건 |
| --- | --- | --- |
| 만족 고객 | 짧고 긍정적 | 6주제를 10턴 안에, `strengths` 2개 이상 |
| 불만 고객 | 담당자 불만을 구체적으로 | `improvements` area=am, severity=high, `complaint_unresolved` 플래그 |
| 단답형 | "네 / 아니요 / 글쎄요" | 주제당 탐침 1회 후 넘어감, 8턴 안에 종료 |
| 장황형 | 한 답에 여러 주제 | 이미 다룬 주제 재질문 없음 |
| 이탈 | 3턴 후 중단 | 48시간 뒤 `abandoned`, 부분 추출 생성 |
| 민감 발언 | 타사·가격 언급 | 후속 질문 없음, `competitor_mention` 플래그만 |

**자동 테스트**

- vitest: 턴 제어(주제 전환·후속 상한·15턴), 출력 JSON 파싱과 재시도, 추출 결과 스키마 검증(zod), 폴백 전환
- Playwright (`e2e/interview.spec.ts`): `/i/[token]` 시작 → 3턴 → 종료, 같은 링크 재진입으로 이어하기, 폼 ending 카드가 `interview_enabled`에 따라 보이고 숨겨짐, 테스트 배치 세션이 집계에서 제외됨
- 모델 호출은 테스트에서 고정 응답(fixture)으로 대체 — 실제 호출은 수동 시나리오에서만

**추출 정확도**

- 파일럿 대화 20건을 다운이 수기로 코딩(추출 스키마와 같은 항목)
- 항목별 일치율 측정, 목표 80%. 미달 항목은 추출 프롬프트 수정 또는 항목 삭제

## 11. 파일럿과 운영 전환

내부 → 우호 고객 → 월간 배치 순으로 넓히고, 단계마다 통과 조건을 미리 둔다. 어느 단계든 통과하지 못하면 가이드·추출을 고친 뒤 같은 단계를 반복한다.

| 단계 | 대상 | 확인하는 것 | 통과 조건 (제안값) | 통과 후 |
| --- | --- | --- | --- | --- |
| 내부 파일럿 | AM 3\~5명이 고객 역할, 테스트 배치(`is_test`) | 소요 시간, 이탈 지점, 추출 정확도, 화면 불편 | 중앙값 10분 이내, 추출 수정률 30% 이하 | 가이드 v2, 추출 v2 |
| 실고객 파일럿 | 우호 고객 5\~10건, 기존 폼과 병행 발송 | 참여율(카드 노출 대비 시작), 완료율, AM 평가("이 요약이 쓸모 있는가") | 참여율 40% 이상, 완료율 폼 대비 -10%p 이내, AM 5명 중 4명 긍정 | 범위 확정(기존 text 문항 제거 여부) |
| 월간 배치 | `cs_monthly_batch` 대상 전체 | 완료율, 플래그 건의 접촉율, 월 비용 | 1절 성공 기준 충족, 비용이 월 한도 내 | 운영 전환 |

**운영 전환 시 결정할 것**

- 기존 text 문항을 템플릿에서 제거할지, 인터뷰 미참여자용으로 남길지
- 전화 인터뷰를 플래그 건·미참여자로 축소할지
- 검수 샘플율(기본 20%)과 검수 담당 분담
- 가이드 개정 주기 (제안: 분기 1회, 수정률·AM 피드백 기준)

**되돌리기**

- 설문별 `interview_enabled`를 끄면 즉시 폼 단독으로 복귀. 데이터·코드 삭제 없음
- 월 한도 도달 시 자동으로 카드 숨김 → 다음 달 재개

- 브랜치 `feat/interview`, 커밋 `feat(interview): …`, Phase 표기는 12절 번호 사용 (예: `feat(interview): 턴·종료 API (12-7)`)
- 되돌리기 어려운 작업(원격 마이그레이션 apply, `main` 머지·프로덕션 배포, 실제 모델 키 등록)은 대상과 영향을 보여주고 확인받은 뒤 실행

- 완료 보고는 실행한 명령과 결과만. 실행하지 못한 항목은 "미실행"으로 표시
